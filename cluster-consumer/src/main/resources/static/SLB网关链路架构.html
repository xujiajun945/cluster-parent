四个必须定下来的决策

01SLB 为什么只能放最前面

SLB 的价值是「一个公网 VIP + 后端多实例」。如果把它插到 Nginx 后面、网关前面，它既没有公网 IP，又和 Nginx 抢同一段内网流量，等于白买。放进来的位置只能是 公网 → SLB → Nginx，让 SLB 成为唯一暴露面，Nginx 退到内网。

02选四层 CLB，还是七层 ALB

CLB（四层）：按端口转发，443 的监听后端统一给 Nginx 组，静态与 API 的分流仍由 Nginx 做。改动最小，Nginx 的缓存、gzip、限流、灰度能力全保留，推荐。
ALB（七层）：可以按 /api/*、/*.js 这类规则直接指向两个后端组，Nginx 只承载静态、网关直接挂 ALB，少一跳。代价是成本更高，且网关前失去 Nginx 这层缓冲。

03Nginx 在中间不是冗余

静态文件本地返回、gzip、expires、单机限流、灰度分支、多站点多域名，这些都是 SLB 做不了的七层事。只要静态资源和 API 还共用一个域名，这一层就该留着。

04两个容易漏的运维点

带宽：静态资源如果全压在 Nginx，SLB 的出流量会按 GB 计费，成本会失控。静态必须上 CDN，SLB 只承载 API 与回源。
网关扩容：Nginx 的 upstream 是静态配置，不会自动感知 Nacos。网关实例动态扩缩时，要么手动/脚本刷 Nginx，要么上 OpenResty + Lua 动态拉取；否则改用 ALB 直接挂网关组，配合弹性伸缩。这是这套拓扑里唯一没有被 Nacos 自动化的接缝。

若后续引入灰度发布，可在 L3 的 Nginx 按 header / cookie 分流到两套网关 upstream，或在 L4 的网关用 Weight 谓词按比例导流，SLB 层不需要任何改动。
